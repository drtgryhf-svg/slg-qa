# Bug 单与质检报告规范

## 严重等级（统一标准，禁止自造）

| 等级 | 定义 | SLG 典型例子 |
|---|---|---|
| **S1 阻断** | 崩溃/卡死/丢单/无法登录/数据丢失 | 新版本登录必崩、支付后不发货且回档 |
| **S2 严重** | 核心功能错误、数值错误、支付异常、**合规风险** | 活动时间差 8 小时、礼包内容挂错、缺概率公示 |
| **S3 一般** | 次要功能错误、显示错乱、部分语言问题 | 俄语文案超出按钮、排行榜并列名次显示错 |
| **S4 轻微** | UI 瑕疵、错别字、样式问题 | 德语文案多一个空格、图标模糊 |
| **S5 建议** | 优化项、体验改进 | 文案歧义修改建议、交互优化 |

优先级 P0–P3 与严重度分开评（P = 什么时候修，S = 坏到什么程度）。S1 默认 P0；S2 默认 P1；依此类推，可人工上调。

## Bug 单字段（每条必填）

```
ID:        BUG-<日期>-<序号>，如 BUG-20260831-001
标题:      [模块] 现象 + 关键条件（英文，≤ 80 字符）
严重等级:  S1–S5 / 优先级: P0–P3
模块:      功能模块（Localization / Store / Event / Battle / UI / Compliance…）
环境:      平台 + 版本号 + 语言 + 服务器（国际服必须带语言和市场）
前置条件:  进什么账号、什么配置
复现步骤:  1. 2. 3.（编号列出，每步可独立执行）
期望结果:  ……
实际结果:  ……
复现率:    必现 / 5 次中 3 次
证据:      截图/录屏路径、日志文件与行号
定位信息:  文本类 bug 必须三要素齐全——文件 + key/行号 + 原文摘录
```

### 文本类 bug 标题示例

```
[L10N][DE] Placeholder {0} missing in march speed description (strings.csv:1204 key: ui.march.speed)
[Store][KR] Probability disclosure page outdated after new gacha pool (config: gacha_pool_v3.json)
```

## 疑似问题 vs 确认问题

- **确认问题**：有证据、可复现 → 正常 bug 单
- **疑似问题**：脚本标出但可能是误报（专有名词、刻意设计）→ 归入报告的"待人工复测"清单，**不占用** bug 计数
- 报告中的问题总数 = 确认问题数；疑似问题单独一行说明

## 质检报告结构

使用 `assets/qa-report-template.md`。顺序：

1. **结论先行**：放行 / 有条件放行（附条件清单）/ 不放行 —— 一句话 + 依据
2. 覆盖范围与方法：检查了什么材料、哪些语言、自动化 vs 人工各覆盖多少
3. 问题汇总表：按严重等级分组的统计 + 明细链接
4. 待人工复测清单：疑似问题、缺材料的项
5. 风险与建议：放行风险、复测范围建议
6. 本次沉淀：新发现的检查项（候选进 skill 的 references/）

## 用语规范

- 中文回复用户；bug 标题英文；报告正文默认中文（国际团队要求英文时切换）
- 不使用"可能有问题""好像错了"这类模糊表述——要么给证据，要么归入疑似
- 每条 bug 的"实际结果"只描述观察到的现象，不写猜测原因；原因分析放单独的"初步分析"字段
